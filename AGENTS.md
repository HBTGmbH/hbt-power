# AGENTS.md

HBT Power is HBT's skills/profile management app: a React webclient plus six Spring Boot services, each in its own top-level `pwr-*` folder. There is no parent POM: every service is a standalone Maven project that is built, tested and deployed on its own. The root [`README.md`](README.md) is the authoritative setup guide; the per-service READMEs only say in a few lines what the service does and point here (#253). The architecture is documented after arc42 in [`docs/arc42/`](docs/arc42/README.md) (context, building blocks, runtime flows, deployment, decisions as ADRs, risks); this file stays the place of the binding rules.

## Build and test

All Java services need **JDK 13** (Lombok in the Spring Boot 2.2 services fails on JDK 16+). The root `.java-version` pins it for jenv. `./mvnw` uses `JAVA_HOME`; in a non-interactive shell run `eval "$(jenv init -)"` first (the jenv `export` plugin then sets `JAVA_HOME`), otherwise `export JAVA_HOME=$(/usr/libexec/java_home -v 13)`.

```shell
cd pwr-<name>-service
./mvnw package                                   # build + all tests (what CI runs: mvn -B package)
./mvnw test -Dtest=ClassName                     # single test class
./mvnw test -Dtest=ClassName#method              # single test method
```

The wrappers in view-profile and edge download `maven-wrapper.jar` on first use (it is gitignored there). Keep `mvnw` executable in Git (`git update-index --chmod=+x`).

Tests need no running infrastructure: the `test` profile uses in-memory H2, and `pwr-view-profile-service` starts an embedded Redis (`com.github.codemonstur:embedded-redis`, which ships binaries for macOS arm64/x64, Linux and Windows). Most tests are JUnit 4.

Webclient (`pwr-webclient`, CRA/react-scripts, TypeScript). Node version is pinned in `pwr-webclient/.nvmrc` (20, as in CI); npm 11 fails to install the dependencies. Env vars in npm scripts go through `cross-env` so they work on Windows:

```shell
npm --prefix pwr-webclient install
npm --prefix pwr-webclient run start:local       # dev server on :3000 against local services, no login
npm --prefix pwr-webclient run build
```

There are no webclient tests at the moment.

## Local run

`docker compose up -d` (or `podman compose` / `docker-compose`) starts MariaDB on host port **3307** (`skill`, `profile`, `report` DBs, root/`changeit`) and Redis on 6379 (password `changeit`) in their own `hbt-power` network. Port 3307 keeps it clear of other local MySQLs; the `localDev` JDBC URLs and the seed URLs in the POMs point there. Start services with the `localDev` Spring profile: IntelliJ run configs in `.run/` (`[localDev] Backend` starts all but the edge service), or from a terminal `./mvnw package -DskipTests` and then `java -jar target/<name>.jar --spring.profiles.active=localDev` from inside the service folder. Sample data: `./mvnw sql:execute` in profile/skill service, report template: `./mvnw exec:exec` in report service. Tables are created by Hibernate, so start the services once before seeding.

## Architecture

| Service | Port | Storage | Calls |
|---|---:|---|---|
| `pwr-edge-service` (Spring Cloud Gateway, Boot 2.7) | 9000 | – | routes to all |
| `pwr-skill-service` | 9003 | MariaDB + Lucene index | – |
| `pwr-profile-service` | 9004 | MariaDB | skill, view-profile, statistics, report |
| `pwr-report-service` (BIRT → .docx) | 9005 | MariaDB | profile, view-profile |
| `pwr-statistics-service` (Boot 2.7) | 9007 | Redis | profile, skill |
| `pwr-view-profile-service` | 9008 | Redis | skill, profile, report |

- **Authentication lives only in the edge service, the check per consultant in each service** (#255). The edge validates Azure AD JWTs and enforces the `Power.User` / `Power.Admin` roles per path (`pwr-edge-service/.../filters/SecurityConfig.java`), then routes `/pwr-<service>/**` to the service. The backend services have no authentication of their own. Who is logged in reaches them only through the headers `X-Pwr-User-Login`, `X-Pwr-User-Initials` and `X-Pwr-User-Admin` (`true`/`false`), which the edge sets from the verified token (`AccountHeadersFilter`) after removing any a client sent; it sets `X-Pwr-User-Admin` on every request. **Admin paths have two layers** (#260): the edge rejects every path that is not normalized with `400` before its path rules (`NormalizedPathFilter`: `.` and `..` segments, `//`, `;`, encoded `/`, `\` or `%`, encoded characters that need no encoding such as `%2e` or `%61`), since the services behind normalize the path themselves and would otherwise map a path the edge doesn't take for `/admin` onto an admin endpoint; and every service with `/admin` endpoints (profile, skill, report, view-profile, statistics) answers `403` there itself when `X-Pwr-User-Admin` is `false` (`AdminAccessInterceptor`, by the mapping Spring MVC chose, not the text of the path). **Rule for the whole app:** the services read the logged-in user only from these headers, never from a request body, a path or a query parameter, not even in a call between services: a service that calls another passes the login and initials on (like the view-profile service on export, #214). Initials in a path say which profile a request is about, not who is logged in. In production an ingress maps `/api/<service>/**` the same way.
- **A user reads and changes only the own data, an admin everyone's** (#255). Profile, report, view-profile and statistics service check it themselves (`security/ConsultantAccess`): `ConsultantAccessInterceptor` compares the path variable `{initials}` of every endpoint with `X-Pwr-User-Initials` (ignoring case), data found by an id (document, profile picture, view profile) is checked with `ConsultantAccess.check(owner)` where it is loaded, and documents only come from the view-profile service (#262): `POST /report` and `/report/preview` of the report service answer `403` to every request through the edge, even of an admin, and to a view profile whose owner (`viewProfileInfo.owner`) is not the consultant of the initials in the body. A whole profile is only read (`GET /profiles/{initials}`), never replaced from a body (#261). Without `Power.Admin` and without a match the answer is `403`; a request without `X-Pwr-User-Admin` did not come through the edge (a call between services, or local development) and may access everything. So: name the consultant a path is about `{initials}`, check the owner of anything loaded by an id, and put personal data about others that only the admin area needs under `/admin` (who uses a skill or profile element, uploading profile pictures). Open to every user by decision: the consultant search (`POST /statistics/consultant/find/skills`), `GET /consultants/names` and the cluster info (`/statistics/network/consultant/{initials}`). An id in a body must belong to the profile in the path, for admins too (`ProfileEntryService.requireInProfile`, `ViewProfileOperationService.isOwner`). The webclient opens no other profile for a user (`OIDCService.mayOpenProfile`).
- **Skill tree changes are admin-only** (#178): everything that creates, moves, deletes or localizes skills and categories, deletes versions or rebuilds the index lives under `/admin/skill/**` and `/admin/category/**` of the skill service (`SkillAdminController`, `CategoryAdminController`), which the edge restricts to `Power.Admin`. Outside `/admin` there are only reads plus what a consultant does while editing a profile: `POST /skill?qualifier=` puts an unknown skill into "Other", `POST /skill/{id}/version` adds a version.
- **Report templates are admin-only** (#203): uploading, changing and deleting them lives under `/admin/template` of the view-profile service (`ReportTemplateAdminController`), their files under `/admin/file` of the report service, both restricted to `Power.Admin` by the edge. The creator comes from `X-Pwr-User-Login`. Outside `/admin` there are only reads (`GET /template`); export and preview read the files directly from the database.
- **Managing consultants is admin-only** (#218): listing, creating, changing and deleting consultants and the consultant selection live under `/admin/consultants` of the profile service (`ConsultantAdminEndpoint`); the statistics service loads its copy from there too. Outside `/admin` there are only `GET /consultants/{initials}` (the own profile) and `GET /consultants/names` (#216). Deleting a consultant (only an inactive one) deletes everything about the consultant (#240): first the view profiles (view-profile service) and the exported documents (`DELETE /admin/report/{initials}` of the report service, `ReportClient`), then the notifications, the profile, the profile picture and the consultant; if another service fails, the consultant stays and deleting again deletes the rest. The statistics load their copy again after the commit. Documents the consultant exported for others stay, and so do the profile elements and skills of the tree the consultant used.
- **Housekeeping** (#242): the data lies in several databases, references between them are bare initials and ids, and some deletes are not transactional, so left-overs remain. Every service reports the inconsistencies of the data it stores itself and cleans them itself: `GET /admin/housekeeping` lists its checks (`HousekeepingFindings`: key, count, up to ten examples, or an error), `DELETE /admin/housekeeping/{check}` deletes what the check finds at that moment and logs count and ids. What it needs from another service it only reads there (the initials of all consultants from `GET /consultants/names`, the files the templates point to from `GET /admin/template/files`, the stored files from `GET /admin/file`); it never deletes there. If that service doesn't answer, or answers with no consultant at all, the check reports an error instead of findings and can't be cleaned. The checks: profile service: rows of `profile_entry` without an entry type, entries, projects and skills no profile holds, notifications about entries that are gone, pictures no consultant shows; report service: documents of unknown initials, documents still `RUNNING` after an hour, files no template points to; view-profile service: view profiles of unknown initials or without an owner, templates whose file is gone. Data without a profile changes no profile, so the statistics need no reload. The admin page *Housekeeping* (`modules/admin/housekeeping`) asks every service on its own. Unused profile elements and own skills are no left-overs but valid entries (#227, #229). **Rule:** whoever adds a reference across services or a delete that is not transactional adds a check to the service that stores the data.
- **Service-to-service calls use `RestTemplate`** (Feign is gone since 2023) with base URLs from `pwr-<name>-service-url` properties. Defaults are docker-compose hostnames; the `localDev` profile overrides them to `localhost`.
- **Data flow:** profile service owns consultants and their profiles; skill service owns the skill tree and search. View-profile service builds editable "view profiles" (snapshots of a profile for one export) in Redis and sends them to the report service, which maps them onto the BIRT data model and renders the report (DOCX, stored in the report history). Only the view-profile service lets the report service make a document, from a view profile it loaded by its id and checked against the initials (#262). The export passes `X-Pwr-User-Login`/`X-Pwr-User-Initials` on to the report service, which stores who exported (name looked up in the profile service) and the description of the view profile with the document (#214). The report preview (generate dialog, report manager) takes the same path but is rendered as PDF in memory and not stored (`GET /view/{initials}/view/{viewProfileId}/{templateId}/preview` → `POST /report/preview`).
- **Statistics** keep their own copy of all consultants and profiles in Redis, loaded from the profile service (`GET /admin/consultants`) at start and then hourly. Everything the statistics service answers, including who uses a skill or an entry in the admin profile elements, comes from this copy. A change of many profiles at once (merging skills #205, renaming, merging and deleting skills and profile elements #227–#229) lets the profile service reload it after the commit (`POST /admin/consultants/refresh` of the statistics service, `Power.Admin` at the edge; `StatisticsClient.refreshConsultantsAfterCommit`); the webclient caches who uses a skill or profile element (`statisticsReducer.skillUsageInfo`, `nameEntityUsageInfo`) and drops those entries after such a change.
- **Schema management:** no Liquibase/Flyway. `ddl-auto: update` locally (`localDev`) and, since #27, in production too (env `DB_HIBERNATE_DDL_AUTO` in the deployment): Hibernate adds new tables and columns on start. It never drops, renames or changes a column, a type or data, so such changes need hand-written SQL for production (see `pwr-profile-service/fix-id-columns.sql`).
- **Commit instead of version:** a state is identified by commit hash and commit time; the versions in `pom.xml` and `package.json` mean nothing and are not maintained (#77, no `SNAPSHOT`). Every service publishes its commit at `GET /actuator/info` (`git.commit` from the `git-commit-id-plugin`, only branch, commit id and time), the edge at `/pwr-edge-service/actuator/info`, the webclient in `build_info.json` (`compileBuildInfo.js`). Only `health` and `info` are published. The info icon in the app bar shows the commits, together with the logged-in account.
- **Fonts in PDFs** (`PdfFonts`, report service): the templates use the HBT font Simplon Norm, which is licensed and must never be committed or baked into an image. Production mounts its files at `/fonts` (`export.font-directory`, volume in `HBTGmbH/pwr-compose-deploy`); without them the image's Noto Sans stands in, weight for weight. Old templates' Arial maps to Simplon Norm too. iText 2.1.7 in BIRT cannot subset `.otf` fonts with CFF outlines, so those are embedded whole; a PDF without `%%EOF` is reported as a rendering error instead of being delivered.
- **Localizations** of skills and categories (`LocalizedQualifier`, ISO 639-2, maintained in the admin skill tree) are only shown when a view profile has a language (`ViewProfile.localization`, #174). The name of the skill tree stays the key everywhere (the view-profile service finds skills and categories by it); the translation goes into `localizedName` next to it and replaces the name only in the report.
- **Names compare ignoring case** (#207): the MariaDB collation (`utf8mb4_uca1400_ai_ci`) ignores case and accents, so `findOneByQualifier(".Net")` finds `.NET`. Name comparisons in Java that decide the same thing need `equalsIgnoreCase`. The tests run H2 with `IGNORECASE=TRUE` to behave alike (accents are not covered). H2 is more lenient than MariaDB elsewhere too: it accepts `in ()` for an empty list, MariaDB rejects it, so guard every `in :list` against an empty list. A test of a delete flushes (`entityManager.flush()`), otherwise the rollback of the test hides a violated foreign key (#243). Merging a spelling in another case into a skill renames it in the profiles to the name of the skill tree and leaves the tree as it is. Names of profile elements are saved without spaces at the ends, and a blank name never becomes one (#215): a profile entry without a name is rejected with `400`, an emptied client, broker or role is none.
- **Skill names are normalized to the skill tree** (#208): a skill name in any case or an alias stands for the name of the skill in the tree; names the tree doesn't know stay. Saving a new skill (profile service, `ProfileEntryService`) only takes over the spelling of the tree (`.net` → `.NET`); **aliases stay as typed** in the profile. Everything that reads profiles uses the tree name: the statistics service normalizes the consultants right after loading them (`SkillNameNormalizer`, `GET /skill/tree`, property `pwr-skill-service-url`) and the skill names in requests; the view-profile service names display and project skills like the tree (`SkillTreeLookup`, one lookup per name and view profile); the list of used skills in the admin profile elements (`GET /suggestions/skills` of the profile service) shows each skill once under its tree name. Skills that end up with the same name in one profile or project become one with the higher rating (and the versions of both in the view profile).
- **Renaming, merging and deleting across all profiles** (#227–#230), all under `/admin` of the profile service:
  - Profile elements (`NameEntity`: companies, roles, languages, qualifications …): `NameEntityAdminEndpoint` under `/admin/name-entities` (who uses one, rename, merge into another of the same type, delete, delete all unused of a type). The old name of a renamed or merged element goes into `name_entity_former_name`; a consultant typing a former name gets the element (`ProfileEntryService.validateNameEntity`).
  - Skills: `POST /admin/skills/rename` and `DELETE /admin/skills?name=` (`AdminEndpoint`), which first change the skill tree (`/admin/skill/rename`, the old name becomes an alias; `DELETE /admin/skill/{id}`), then the profiles and projects. Merging stays #205.
  - View profiles stay snapshots. *Aktualisieren* (`ViewProfileMergeService`) matches the old entries to the renamed or merged ones through the former names (`GET /admin/name-entities/former-names`, `FormerNames`) and the skill tree (`SkillTreeLookup`), so they keep their settings (shown, order, versions).
  - Hibernate: the hash of a `ProfileEntry` depends on its `NameEntity`, so after repointing entries the profile's set is rebuilt before removing from it, or Hibernate detaches the kept ones. An entry removed from a profile collection stays as a row with `profile_id` null (a deleted project no longer does since #243: `deleteProject` deletes the row, whose skills are those of the profile): count usage only through joins from `Profile`, and delete those rows together with the element. Old data also has rows in `profile_entry` without a row in the table of an entry type (#236): Hibernate can't load them as the abstract `ProfileEntry`, so load entries per entry type (`select e from SectorEntry e …`), never `from ProfileEntry`, and remove what is left with native SQL.
- **Skill search** uses Hibernate Search/Lucene; the index is rebuilt on every start and via the `/admin/skill/lucene/index` endpoint. Locally it lives in `pwr-skill-service/lucene-data` (gitignored), the tests keep theirs in memory (`local-heap`).
- **Spring profile syntax differs by Boot version:** 2.2 services use `spring.profiles: localDev` in multi-document YAML, the 2.7 services (edge, statistics) use `spring.config.activate.on-profile`.
- Java base packages differ per service (`de.hbt.pwr.profile`, `de.hbt.power`, `de.hbt`, `de.hbt.pwr.view`, `de.hbt.pwr`).

### Webclient

- Redux state in `src/reducers`, components in `src/modules` (`admin`, `home` = profile editing, `general` = shared components).
- Navigation: both areas have a menu behind the burger in the app bar (`PowerToolbar`, `AdminMenu`, #212). What is selected on a page is in its URL (`Paths`, built with `Paths.build`), so reload and back work: the id selects, a slug of the name after it (`StringUtils.slug`) is only for reading; names that are no ids (used skills) go into a query parameter.
- Backend access goes through the axios wrappers in `src/clients` (`XyzServiceClient.instance()`), which handle the loading spinner, payload extraction and error alerts, and re-throw errors. Small edits that show right away (switching, moving, sorting on the view profile page) use `patchInBackground`: no overlay, which would get in the way of every click, but a counter of background requests (`crossCutting.backgroundRequests`) that the page shows as a thin bar. `dispatch` of a thunk doesn't return its promise (`AsyncActionUnWrapper`): a component that needs the result passes a callback to the action creator.
- Binary content (profile pictures, report previews) is loaded through these clients as a blob and shown through a blob URL, never as `src`/iframe URL pointing at the API: those requests carry no token and the edge rejects them. Profile pictures go through `PwrProfilePicture` (`modules/general`), which caches them per picture id.
- Runtime config: `config.js` contains `#PLACEHOLDER`s that `configure_api.sh` replaces from env vars when the nginx container starts. `start:local` sets `REACT_APP_LOCAL_DEV=true`, which serves `config.local.js` and proxies `/api/<service>` to the local ports (`src/setupProxy.js`) and skips Azure login (`CONFIG.LOCAL_DEV`).
- Static files: images, CSS and data live in `src/` and are imported, so the build serves them with a content hash under `/static/`, which nginx (`default.conf`) caches as `immutable`. `public/` only holds `index.html` and `favicon.png`; everything outside `/static/` is served with `no-cache`.
- Conventions: render user-facing text through `PowerLocalizer`; use string values in enums (Redux); prefer components from `modules/general`, e.g. `PwrButton` / `PwrIconButton` with the icon on the right, icon buttons need a tooltip.
- Dates without time (#26): every `LocalDate` field of the services (profile entries, birth date, view profile) stays the string `"YYYY-MM-DD"` (`LocalDate` in `utils/DateUtil.ts`) in models and Redux state; it sorts and compares as a string. Only `PwrDatePicker` converts it to a `Date` for the picker and back, so no `new Date("YYYY-MM-DD")` (UTC midnight) or `toISOString()` (shifts local midnight to the day before). A real date type is only worth it once the webclient calculates with dates. Timestamps (`LocalDateTime`) remain `Date`.
- Names of colleagues (#216): the app names consultants by their short name, the first name if no other active consultant has it, otherwise with as many letters of the last name as it takes (`Kai B.`, `Kai Br.`), the full name with initials if even that is the same. The profile service computes it (`ConsultantShortNames`) and serves it to every user at `GET /consultants/names` (initials, short and full name, nothing else); the webclient loads it once after the login and after every change to a consultant (`consultantNames` in Redux) and shows it through `PwrConsultantName` (`modules/general`) with the full name in the tooltip. The full name stays in export documents, the delete confirmation and the edit fields; the title of a consultant is the job title and belongs to neither name.
- Own profile: the initials of the logged-in account come from the ID token claim `mailnickname` (`OIDCService.getCurrentAccount`). Without the `Power.Admin` role the profile select opens that profile right away; admins choose from the consultant list (`ConsultantSelect`), which the edge only serves to them. Unknown initials get a message, not an error (`ConsultantClient.findConsultant`).
- Profile check (#139): the profile service computes what is missing or outdated (`ProfileCheckService`, thresholds under `profile-check` in its `application.yml`); the webclient shows it right after the welcome card of the overview, in the generate dialog and on the consultant tiles. A hint links to where it is fixed; sections of the profile page have anchors (`#profile-section-<SECTION>`).
- Unsaved changes in a project: `PWR_HISTORY.block` (registered in `index.tsx`) holds back every navigation and asks through the `UnsavedChangesDialog`. Actions that leave a project without navigating (select another project, add a project, admin area, logout) go through `confirmLeavingUnsavedChanges` (`reducers/navigation/UnsavedChanges.ts`). Saving, cancelling and deleting don't ask.
- Colours (#201): errors and destructive actions in `palette.error` (red), warnings that are no errors (outdated, can't be undone) in `palette.warning` (dark orange), both in `PowerTheme.ts`. The HBT orange (`PWR_ACCENT`) is an accent only: a bar, a border, or an area with dark blue text on it; never the colour of text and never behind white text (2.3:1 on white). Text needs a contrast of 4.5:1, icons and other graphics that carry meaning 3:1. No colour names or hex values for text: Material-UI components take the theme (`color="error"`), `makeStyles` reads `theme.palette`, `index.css` uses the CSS variables `--pwr-error`, `--pwr-warning` and `--pwr-accent`, which `PwrThemeColors` sets from the theme.
- Input fields use the Material-UI `filled` variant (grey area), set as default in `PowerTheme.ts`: don't set `variant` per field. Components the theme doesn't reach (`ChipInput`, `FormControl` around a `Select`) get `variant="filled"` explicitly. Disabled and read-only fields have no grey area, so read mode looks different from edit mode.
- Form spacing on the 8 px grid of `theme.spacing` (`modules/general`): `PwrSpacer` with `tight` (8 px: label and value, chips, one row), `field` (16 px, default: between the fields of a group) and `section` (32 px: between sections, before the button bar). A group with a heading is a `PwrFormSection` (section space above), chips or small buttons in a row a `PwrRow`. No inline margins and no single classes for spacing in forms.
- Lists and small tables: `PwrListTable` (`modules/general`, #199), in the look of the view profile tables (#149): grey header row of 12 px, rows of 14 px and at least 40 px with a line between them. With `onSelect` the rows are buttons (arrow keys move between them) and the selected one is highlighted.
- Form buttons: `PwrFormActions`. The main action with text and highlighted (`Bearbeiten` in read mode, `Speichern` in edit mode), `Abbrechen` as a text button next to it, `Löschen` set apart on the right in the error colour. Dialogs with a form use it too, inside `DialogActions` (`noSpace`, own label and icon for the main action, e.g. `Erstellen`). Further actions go between the main action and `Abbrechen` (`Zurück` in a wizard). Confirmation dialogs use `PwrConfirmActions`: the confirming action highlighted, in the error colour if it destroys something (`Löschen`, `Änderungen verwerfen`), the rejecting one as a text button. Every delete asks first: through `makeDeferrable` with its own `ActionType`, registered in `DeferredActionMiddleware`. In the admin area (#181) the question is not enough: the action creator passes `confirmByName` to `makeDeferrable` (built with `confirmDeleteByName`), the dialog names the entry and what goes with it, and `Löschen` only becomes active once the name (initials for a consultant, the translation for a localization, the version) was entered twice, exactly as written apart from spaces at the ends. Only emptying the trash keeps the simple question. In lists (profile entries, projects, export documents, view profiles) delete is a trash icon per entry, not a button of the form; the view profiles (#213) are a `PwrListTable` with icon buttons for `Generieren`, `Bearbeiten` and `Löschen` per row, the newest three on the overview and all under `/app/<initials>/views`.

## CI

One GitHub Actions workflow per folder (`.github/workflows/<folder>.yml`), path-filtered (the same filter for `push` and `pull_request` via a YAML anchor). Each has two jobs:

- **`check`** ("Build and test") on pull requests against `main`: build with Zulu JDK 13 / Node 20, run tests, build the image without pushing. Read-only token, dependency caches allowed.
- **`publish`** on push to `main` (or manually): the same build, then push the image to `ghcr.io/hbtgmbh/hbt-power/<folder>`. Only this job has `packages: write`, and it uses no dependency cache, so nothing cached by a PR run can end up in an image.

A PR only shows checks for the folders it touches. Workflow changes must pass actionlint and zizmor.

- **`lint-actions.yml`** ("Lint GitHub Actions") runs on every PR against `main` and every push to `main` that touches `.github/**`: actionlint with shellcheck and zizmor (online audits), with `contents: read` only. Locally: `uvx --from actionlint-py --with shellcheck-py actionlint` and `uvx zizmor --persona regular .` from the repository root.
- **Pinning policy** in `.github/zizmor.yml`: first-party actions (`actions/*`, `github/*`, `docker/*` …) and `HBTGmbH/*` with a major tag (`@v7`), all others with the full commit SHA plus a `# vX.Y.Z` comment.
- **Dependabot** (`.github/dependabot.yml`) opens a PR for new action versions once a week, at the earliest 7 days after a release (`cooldown`). For a new major version check that every input the workflow uses still exists in the new `action.yml`. Maven and npm are not covered.

## GitHub workflow

- **Repository:** `HBTGmbH/hbt-power` (take the owner from `git remote get-url origin`). It is **public**.
- **No operating environment details on GitHub:** no host names, deployment or management URLs, tenant/client IDs, connection strings, secrets, or queries against live systems in issues, PRs, commit messages, code, comments, docs or screenshots. Write „the production environment“, `<host>` instead. A later edit doesn't help: GitHub keeps the edit history and git keeps the commit.
- **Issue structure:** current behaviour (*Ist-Zustand*, with references into the code), desired behaviour (*Wunsch*), and acceptance criteria as a checklist. Mockups (ASCII sketch or screenshot of the local webclient with seed data) and ` ```mermaid ` diagrams are welcome, e.g. a `sequenceDiagram` when a change crosses services, but not required.
- **Issue type:** set after creation via GraphQL: `Task` `IT_kwDOAYn5ks4AV-6C`, `Bug` `IT_kwDOAYn5ks4AV-6D`, `Feature` `IT_kwDOAYn5ks4AV-6H`.
  ```bash
  gh api graphql -f query='mutation { updateIssue(input: { id: "<node_id>", issueTypeId: "<type_id>" }) { issue { number issueType { name } } } }'
  # node_id: gh api repos/HBTGmbH/hbt-power/issues/NNN --jq .node_id
  ```
- **Branches:** `feature/<issue>-<short-description>` (new capability) or `bug/<issue>-<short-description>` (defect), branched from an up-to-date `main`. One issue per branch and PR, no bundling, except for small fixes (next bullet). No direct pushes to `main`.
- **Small fixes along the way:** fix small defects you come across directly in the current branch, as long as they don't put the current ticket at risk. Small means: an obvious defect, a few lines, cause and fix clear without further analysis, no change to an API contract, entity, Redis model or the edge path rules, and verifiable within the current test and click-through. Commit it separately with the current issue ID (`#12 - Nebenbei: …`) and list it in the PR under *Beschreibung*. Anything bigger, or anything that would delay or blur the current ticket, gets its own issue.
- **Line endings:** LF for all text files, CRLF only for `*.cmd`/`*.bat`, set in `.gitattributes`. Commits that only reformat (like the normalization in #46) go into `.git-blame-ignore-revs`, so `git blame` and GitHub skip them (locally: `git config blame.ignoreRevsFile .git-blame-ignore-revs`).
- **Commit messages:** every commit starts with the issue ID, then ` - `, then a short description, e.g. `#12 - Skill-Suche ignoriert Groß-/Kleinschreibung`. Without an issue (typos, trivial housekeeping): `#noissue - …`.
- **Pull requests:** fill in `.github/pull_request_template.md`, put `Closes #NNN` in the body, and include: *"Reviewed AGENTS.md; changes comply with architecture and security guidelines."*

## Definition of Done

Apply this at the end of each task to what the task changed, and report which items apply and whether each is satisfied. A task is done when all applicable items are true.

### Build and tests
- [ ] `./mvnw verify` passes in every changed `pwr-*-service` (JDK 13)
- [ ] `npm run build` passes if `pwr-webclient` changed
- [ ] All existing tests pass; new backend behaviour is covered by tests

### Services
- [ ] **API contracts:** if an endpoint changed, every caller is adjusted in the same PR: the `RestTemplate` clients in the other services and `pwr-webclient/src/clients`
- [ ] **Logged-in user:** whoever acts (creator, exporter, confirmer …) is read from `X-Pwr-User-Login`/`X-Pwr-User-Initials` only, never from a body, path or query parameter; calls between services pass these headers on
- [ ] **Edge security:** new or moved endpoints are checked against the path rules in `pwr-edge-service/.../filters/SecurityConfig.java`; admin functionality must live under a path the edge restricts to `Power.Admin`
- [ ] **Own data only** (#255): an endpoint about one consultant has the initials as path variable `{initials}`, or checks the owner of what it loads by an id with `ConsultantAccess.check`; a test shows `403` for another user and access for the owner and an admin
- [ ] **Redis compatibility:** changes to Redis models (`ViewProfile`, `ReportTemplate`, statistics models) keep existing stored data readable. Spring Data Redis stores an object as a hash with one entry per field, reads only the fields of the model and rewrites the whole hash on save. So renaming a field or changing its type needs a migration; removing one doesn't (the old entry is passed over and goes with the next save, #179); a new field is missing in old data and needs a default
- [ ] **Database schema:** there is no Liquibase/Flyway. New tables and columns are added by Hibernate on start (`ddl-auto: update`); a change it can't do (rename, drop, type change, data migration) comes with a SQL script for production (like `pwr-profile-service/fix-id-columns.sql`). Every schema change is listed under *Operations / Deployment Notes* in the PR
